3Dmap — Migration Odoo 18

Migration et stabilisation d'un ERP Odoo en production (v17 vers v18), avec debug SQL bas niveau, fiabilisation Linux et remise en accessibilité publique. Stage de deuxième année réalisé chez 3Dmap (février 2026).

  • Odoo 17 → 18
  • PostgreSQL
  • Python 3.12
  • Linux
  • systemd
  • OpenUpgrade

Voir l'instance Odoo Attestation Rapport

Contexte & objectifs

Dans le cadre de mon stage chez 3Dmap, j'ai travaillé sur la migration d'une instance Odoo de production vers une version majeure. L'objectif n'était pas uniquement de migrer la base, mais surtout de rendre l'ERP stable et exploitable après la bascule.

  • Migrer la base de données d'Odoo 17 vers Odoo 18.
  • Assurer la compatibilité des modules custom et OCA.
  • Corriger les erreurs critiques post-migration (SQL et HTTP).
  • Stabiliser la configuration serveur Linux.
  • Rendre l'instance accessible publiquement.

Stack technique

  • ERP : Odoo 17 vers Odoo 18
  • Serveur : VPS OVH (Linux)
  • Base de données : PostgreSQL
  • Runtime : Python 3.12
  • Service : systemd
  • Outils : ligne de commande, psql, logs Odoo
  • Migration : logique OpenUpgrade
  • Modules : custom 3dmap_* + modules OCA

Réalisations

1) Migration de la base vers Odoo 18

Après migration, la base semblait en version 18, mais l'instance ne démarrait pas correctement et retournait des erreurs 500.

  • Vérification SQL de l'état du module base.
  • Analyse complète des logs : /var/log/odoo/odoo18.log.
  • Correction d'erreurs de manifest (version invalide).
  • Nettoyage de la configuration openupgrade_framework.
SELECT name, state, latest_version
FROM ir_module_module
WHERE name='base';

2) Debug SQL post-migration

Odoo générait des erreurs UndefinedColumn, signe que le schéma PostgreSQL n'était pas parfaitement aligné avec les attentes d'Odoo 18.

  • Analyse des requêtes SQL produites par Odoo dans les logs.
  • Ajout manuel de colonnes manquantes dans la table website.
  • Disparition des erreurs InFailedSqlTransaction.
  • Rétablissement progressif du backend.
ALTER TABLE website ADD COLUMN IF NOT EXISTS shop_gap integer;
ALTER TABLE website ADD COLUMN IF NOT EXISTS ecommerce_access boolean;

3) Configuration serveur et service Linux

Le service Odoo crashait à cause d'une mauvaise configuration (db_port invalide, paramètres incomplets).

  • Correction des paramètres db_port, proxy_mode, dbfilter.
  • Vérification du lancement via systemd.
  • Contrôle des ports d'écoute.
sudo systemctl restart odoo18
sudo systemctl status odoo18
sudo ss -lntp | grep 8070

4) Résolution des erreurs HTTP (302 / 500)

Le comportement différait entre localhost et le domaine public avec des redirections et erreurs 500.

  • Désactivation temporaire de proxy_mode=True (sans Nginx).
  • Tests curl en local puis via domaine.
  • Analyse des headers HTTP et vérification DNS/port 8070.
  • Instance accessible sur dev.3dmap.fr:8070.

5) Modules custom et OCA

Plusieurs modules étaient marqués installed en base, mais ignorés au démarrage (not installable, skipped), avec risque de vues cassées et dépendances incomplètes.

  • Analyse croisée entre ir_module_module, addons_path et manifests.
  • Identification des modules critiques à traiter en priorité.
  • Stratégie de stabilisation progressive du registry Odoo.
  • Développement de module sur mesure et remise en production.

Compétences mobilisées

  • Migration d'ERP complexe entre versions majeures.
  • Debug SQL bas niveau sur PostgreSQL.
  • Analyse de logs et stack traces Python.
  • Administration Linux et gestion de service systemd.
  • Diagnostic HTTP (302/500, cookies, proxy mode).
  • Remise en production d'un service métier critique.
  • Approche méthodique : fix, test, logs, correction.
